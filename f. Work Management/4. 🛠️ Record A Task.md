# 🛠️ Record A Task

## 1. Bound one executable outcome

State one result that can be completed independently. Split the request when
two outcomes can finish, block, or be accepted independently.

Do not create a Plan merely because a Task is worth remembering. Use Plan Work
only when coordination, dependency reasoning, gates, or several independently
stateful nodes are required.

## 2. Allocate the Work ID

Inspect existing `.project/Execution/Tasks/` Task IDs and select the next
unused `T<number>` value using zero padding already established by the
repository. Use `T001` when none exists.

The Work ID is permanent. Do not renumber closed or archived Tasks to remove
gaps.

## 3. Create the Task file

Create `.project/Execution/Tasks/` when it does not exist. Name the file:

```text
<Work ID> <concise outcome title>.md
```

Use this minimum representation:

```markdown
---
description: >-
  `Consult when` *task T001 must be resumed or inspected* `to` **recover
  its outcome, current state, and next action**.
work:
  id: T001
  type: task
  state: ready
  updated: YYYY-MM-DD
---

# T001 — <Outcome title>

## Outcome

<Observable result.>

## Acceptance conditions

- <Condition that proves the outcome is complete.>

## Current state

<What is true now that another agent needs in order to act correctly.>

## Next action

<The next concrete action.>
```

Leave `uid` absent when creating a new controlled artifact; Organizing mints
it on refresh.

## 4. Add only required execution fields

Add these sections or metadata only when the Task needs them:

- `priority` when several ready Tasks compete for attention;
- `relations` when another Work Object affects this Task;
- `blocked-by` evidence when state is `blocked`;
- an execution checklist when several local steps share one acceptance boundary;
- Decisions when a choice must survive handoff but does not require independent
  provenance;
- Evidence when completion depends on a check another agent cannot reconstruct;
- a Handoff log when more than the current-state snapshot is needed.

Do not add empty template sections for possible future complexity.

## 5. Establish actionability

Set `state: ready` only when the outcome and acceptance conditions are clear
and every prerequisite for starting is satisfied.

Otherwise use `captured` or `blocked` and name the missing condition.

A Task with an unsatisfied dependency is not made actionable by high priority.

## 6. Refresh controlled state

Run Organizing for the target repository after creating the Task so the
controlled sideband artifact receives a UID and metadata validation.

The Task is now durably registered. It can execute independently.

## 7. Attach a Plan only when needed

When later complexity requires a Plan, create or select the Plan and add a
`coordinates` relationship to this existing Task ID.

Do not copy the Task into the Plan, assign a replacement ID, or move it out of
`Execution/Tasks/` merely because coordinated planning now exists.

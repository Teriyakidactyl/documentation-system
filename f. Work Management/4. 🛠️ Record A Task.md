# 🛠️ Record A Task

## 1. Confirm the work is standalone

Use this procedure for executable work that needs repository-global identity and
lifecycle outside any one Plan.

Do not use the standalone Task allocator for an ordinary Plan-local Task. Put
that Task inside its Plan and use the Plan Document Form.

Do not create a Plan merely because a standalone Task is worth remembering.
Use Plan Work only when several acceptance boundaries require coordination.

## 2. Register the Task through repository automation

Use the Repo Manager Work Management registration operation to allocate the
Task ID and create the initial Task record.

Conceptually:

```text
work register-task
    ↓
read and reconcile .project/metrics.json
    ↓
verify all active and archived Work IDs
    ↓
allocate next T###
    ↓
create Task + advance metrics
    ↓
mint controlled uid when applicable
```

Do not manually choose the next `T<number>` when repository automation is
available.

The Work ID is permanent. Do not renumber closed or archived Tasks to remove
gaps.

## 3. Name and bound the outcome

The registered file is stored beneath:

```text
.project/Execution/Tasks/
```

and begins with its Work ID:

```text
T043 Fix broken README link.md
```

State one result that can be completed independently. Split the request when two
outcomes can finish, block, or be accepted independently.

## 4. Maintain the minimum Task representation

A standalone Task carries:

```markdown
---
uid: <repository-automation-minted when applicable>
description: >-
  `Consult when` *task T043 must be resumed or inspected* `to` **recover
  its outcome, current state, and next action**.
work:
  id: T043
  type: task
  state: ready
  updated: YYYY-MM-DD
---

# T043 — <Outcome title>

## Outcome

<Observable result.>

## Acceptance conditions

- <Condition that proves the outcome is complete.>

## Current state

<What is true now that another agent needs in order to act correctly.>

## Next action

<The next concrete action.>
```

## 5. Use checkbox-backed Steps when needed

When several actions share this one Task acceptance boundary, add Steps as
Markdown task-list checkboxes:

```markdown
## Steps

- [ ] First action.
- [ ] Second action.
- [ ] Verify the result.
```

A Step does not receive its own lifecycle state. If an action needs independent
blocking, review, handoff, or acceptance, split it into another standalone Task
or coordinate it inside a Plan.

## 6. Add only required execution fields

Add these sections or metadata only when the standalone Task needs them:

- `priority` when several ready Tasks compete for attention;
- `relations` when another standalone Work Object affects this Task;
- blocking evidence when state is `blocked`;
- Decisions when a choice must survive handoff but does not require independent
  provenance;
- Evidence when completion depends on a check another agent cannot reconstruct;
- a Handoff log when more than the current-state snapshot is needed.

Do not add empty template sections for possible future complexity.

## 7. Establish actionability

Set `state: ready` only when the outcome and acceptance conditions are clear
and every prerequisite for starting is satisfied.

Otherwise use `captured` or `blocked` and name the missing condition.

A Task with an unsatisfied dependency is not made actionable by high priority.

## 8. Coordinate later without replacing identity

When later complexity requires a Plan, create or select the Plan and reference
this existing standalone Task.

Do not copy the Task's lifecycle state into a Plan-local duplicate, assign a
replacement Work ID, or move it out of `Execution/Tasks/` merely because
coordinated planning now exists.

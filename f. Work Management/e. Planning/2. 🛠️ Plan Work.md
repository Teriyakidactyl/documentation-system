# 🛠️ Plan Work

## 1. State the outcome and acceptance boundary

Write one observable repository outcome. List the conditions that make the Plan
complete and the constraints that remain binding during execution.

Separate the work outcome from the current Plan representation. A Plan can be
restructured without changing what successful work means.

## 2. Use the Plan Document Form

When recording the Plan as Markdown, apply the Plan Document Form under
Document Design Assemblies.

Work Management determines what the Plan means. The Form determines how that
meaning is represented in the file.

Do not invent a competing local syntax for Task state, Steps, or completed
work.

## 3. Establish Plan-local Tasks

Create one Plan-local Task for each independently meaningful acceptance
boundary inside the Plan.

Assign compact local IDs in Plan order, such as `T1`, `T2`, and `T3`.
These are not repository-global Work IDs.

Do not create standalone Task files for ordinary Plan Tasks.

## 4. Add Steps

Break a Task into Steps only when the actions help execution or handoff.

Every Step must be represented by a Markdown checkbox, or be immediately
accompanied by the checkbox that records its completion state.

Keep Steps inside their Task. If an action needs independent lifecycle state,
make it another Plan-local Task rather than inventing richer Step state.

## 5. Establish dependencies and Gates

For every pair where order or coupling matters, determine whether the downstream
Task actually requires an observable upstream condition.

When it does, state what the upstream work must establish before the downstream
Task can safely proceed. Add a Gate when the threshold must be checked
explicitly.

Reject dependencies whose only meaning is "A before B" when no required output
or condition can be stated.

## 6. Add complexity only when needed

Use the least structure that makes execution deterministic enough:

1. Plan-local Tasks with acceptance conditions;
2. checkbox-backed Steps where execution benefits from them;
3. explicit relations when ordering, blocking, or coordination matters;
4. Gates when dependencies need observable sufficiency thresholds;
5. validation timing, cycles, and commitment classification only when the
   problem actually contains them.

Higher formalization does not invalidate a simpler Plan.

## 7. Promote work only when independence appears

When a Plan-local Task needs an identity and lifecycle outside the Plan,
register a standalone Task through repository automation and record the
promotion target.

Do not copy current state into both places. After promotion, the standalone
Task owns its lifecycle and the Plan references it.

## 8. Compute the execution frontier

Identify incomplete Plan-local or referenced standalone Tasks whose
prerequisites and Gates are satisfied now.

Record blocked work with its unsatisfied condition. Keep priority separate from
dependency.

## 9. Write resumable current state

Record:

- current frontier;
- active Task or Tasks;
- blocked work and unmet Gates;
- unresolved decisions;
- changed assumptions;
- next action; and
- repository authority or evidence required for that next action.

Another agent should be able to continue from the Plan file without prior
conversation.

## 10. Maintain current execution truth

Update Task state, Step checkboxes, Gates, acceptance boundaries, and current
state as work changes.

Preserve history only when it has a future retrieval job. Completed Tasks remain
visible according to the Plan Form rather than being moved into separate files
or status folders.

## 11. Close the Plan

When the Plan outcome is satisfied or coordinated work intentionally ends,
apply Close Work.

Ensure every surviving current rule or artifact has its proper owner and every
incomplete residual item has an explicit disposition.

# 📖 Plan Model

## 1. Plan

A Plan is a Work Object whose primary output is a durable execution graph for
one repository outcome.

A Plan has:

```text
Plan
├── outcome and acceptance boundary
├── constraints
├── Nodes
├── Relations
├── Gates
├── current execution state
├── decisions and uncertainty
└── handoff / retained history as needed
```

## 2. Node

A Node is an independently reasoned position in the Plan graph.

Required Plan-local fields are:

```yaml
id: N001
kind: task | investigation | decision | validation | milestone | external-condition | deliverable
state: captured | ready | active | blocked | review | closed
```

When the node is a standalone Work Object, use its Work ID instead of assigning
a duplicate Plan-local identity.

## 3. Relation

A Relation is a named edge. The minimum representation is:

```yaml
from: T001
to: T002
type: requires
gate: G001
```

Use explicit relations when the edge matters independently of node placement.

## 4. Gate

A Gate states the minimum observable condition that permits a transition.

```yaml
G001:
  condition: Work Object vocabulary is stable enough for serialization.
  evidence: Work Model object-kind and state tables.
  threshold: Every serialized field used by T002 has one defined meaning.
```

A dependency without a meaningful threshold is ordering preference, not a hard
execution Gate.

## 5. Coupling

Use these planning-level coupling classes when they improve execution:

| Coupling | Meaning |
|---|---|
| `independent` | Nodes can complete without mutual adjustment. |
| `sequential` | One node supplies a prerequisite for another. |
| `bidirectional` | Two nodes must iteratively converge. |
| `multi-node-cycle` | A cluster requires synchronized iteration. |

Every cycle declares an exit Gate.

## 6. Validation timing

A validation node or Gate can be:

- `immediate` after the producing node;
- `deferred` until dependent context exists;
- `terminal` at outcome acceptance; or
- `continuous` while upstream work proceeds.

A terminal property that cannot be added safely after the fact requires a
continuous upstream check.

## 7. Commitment cost

`reversible` nodes are inexpensive to revisit. `stabilizing` nodes reduce
uncertainty and should fire when sufficient inputs exist. `locking` nodes make
later change expensive and require strong upstream Gates.

Commitment cost is planning information. It is not Task priority.

## 8. Execution frontier

The frontier is derived:

```text
incomplete
AND executable kind
AND all hard prerequisite Gates satisfied
AND no active blocking condition
```

A Plan may record a frontier snapshot for handoff, but the canonical graph must
contain enough information to recompute it.

## 9. Single-file representation

A small Plan can keep the complete graph in one Markdown file:

```markdown
---
description: >-
  `Consult when` *plan P001 must be resumed or inspected* `to` **recover
  its outcome, execution graph, gates, current frontier, and next action**.
work:
  id: P001
  type: plan
  state: active
  updated: YYYY-MM-DD
---

# P001 — <Plan title>

## Outcome
## Acceptance conditions
## Constraints
## Work graph
## Gates
## Current state
## Next action
```

Plan nodes can use compact properties:

```markdown
### T001 — Establish work vocabulary

State: closed
Kind: task

### T002 — Specify storage

State: ready
Kind: task
Requires: T001
Gate: G001
```

## 10. Multi-file representation

Materialize a node as a standalone Work Object when it needs an independent
lifecycle, handoff, acceptance boundary, or retrieval identity.

```text
.project/
├── Planning/
│   └── Plans/
│       └── P001 Work Management.md
└── Execution/
    └── Tasks/
        ├── T001 Establish work vocabulary.md
        └── T002 Specify storage.md
```

The Plan references `T001` and `T002`; it does not duplicate their current
state as a second authority.

## 11. Derived views

Queue, ready list, blocked list, execution frontier, critical path, and
parallelizable-work views are derived projections.

A manually maintained snapshot must be labeled as a snapshot and refreshed from
canonical nodes, relations, Gates, and state when relied on.

# 📖 Plan Model

## 1. Plan

A Plan is a standalone Work Object whose primary job is to coordinate multiple
acceptance boundaries toward one repository outcome.

A Plan becomes an execution continuity source only after its current state is
persisted in storage available to the executing agent after interruption,
handoff, or conversation compaction. Conversation-only Plan state is not
durable work state.

A Plan normally keeps one durable execution model containing outcome and
acceptance, constraints, Plan-local Tasks and Steps, dependencies and Gates,
decisions and uncertainty, current execution state, and next action.

## 2. Authoring work and planned work

**Plan-authoring work** is the work required to discover, reason about, validate,
and record a trustworthy Plan.

**Planned work** is work represented by the Plan whose completion contributes
to the Plan outcome.

**Discovered work** is planned work revealed during guidance discovery,
repository inspection, capability assessment, or execution tracing.

Do not create a Plan Task merely because the author had to perform an activity
to construct the Plan. Promote that activity into planned work only when it
independently contributes to the repository outcome.

## 3. Executor capability reassessment

The authoring agent and later executors may have different harnesses. Every Plan
therefore preserves an execution-time instruction requiring the current
executor to assess materially relevant capabilities and limitations before
entering the execution frontier.

A material capability fact affects safe execution, blocking, validation,
handoff, or acceptance. Examples include bounded reads, pagination/EOF
behavior, durable storage, repository checkout availability, shell/code
execution, timeouts, dependencies, network/external calls, connector
permissions, mutation authority, and specialized tools.

The Plan author’s tool list is not execution truth.

## 4. Plan-local Task

A Plan-local Task is the ordinary executable unit inside a Plan.

Its required semantic fields are:

```yaml
id: T1
state: ready | active | blocked | review | completed | cancelled
acceptance:
  - <observable completion condition>
```

The ID is local to the Plan. A Plan-local Task owns one acceptance boundary.

## 5. Step

A Step is an execution action inside one Plan-local Task acceptance boundary.
Steps do not carry independent lifecycle identity, disposition, Work IDs, or
files.

If an action needs independent blocking, review, handoff, cancellation, or
acceptance, represent it as another Plan-local Task or promote it to a
standalone Task.

The Plan Document Form owns checkbox and visual representation.

## 6. Task state

| State | Meaning |
|---|---|
| `ready` | The acceptance boundary is understood and starting conditions are satisfied. |
| `active` | The Task currently holds execution attention. |
| `blocked` | A named unsatisfied condition prevents progress. |
| `review` | Execution is materially complete and a review or validation condition remains. |
| `completed` | The Task acceptance boundary is satisfied. |
| `cancelled` | The Plan no longer intends to satisfy the original Task acceptance boundary. |

The explicit state is canonical. Markdown callouts and strike-through are Form
representations of that state.

## 7. Relation

A Plan relation is a named edge between Plan-local Tasks, standalone Work
Objects, Gates, or relevant conditions. Use explicit relations only when an edge
affects safe execution, handoff, or completion.

## 8. Gate

A Gate states the minimum observable condition that permits downstream work to
start or close.

A hard dependency without an observable threshold is only an ordering
preference. Every cyclic dependency declares an exit Gate.

## 9. Validation timing

Validation may be immediate, deferred, terminal, or continuous. A terminal
property that cannot be added safely after the fact requires a continuous
upstream check.

## 10. Commitment cost

`reversible`, `stabilizing`, and `locking` classify the cost of later
change. Commitment cost is planning information, not priority.

## 11. Execution frontier

The execution frontier is derived from incomplete executable work whose hard
prerequisite Gates are satisfied and which has no active blocking condition.

A Plan may record a frontier snapshot for handoff but must preserve enough
current state to recompute it. Executor capability reassessment occurs before an
agent relies on the frontier as immediately executable.

## 12. Single-file default

Plan-local Tasks and Steps remain in the durable Plan artifact by default.
Do not allocate repository-global Task IDs merely because a Plan contains
several Tasks.

## 13. Promotion to standalone Task

Promote a Plan-local Task only when it needs durable lifecycle or retrieval
independence from the Plan. Promotion allocates a repository-global Work ID
through repository automation and stops duplicate lifecycle state in the Plan.

## 14. Representation boundary

This Reference owns Planning semantics, not Markdown layout.

The Plan Document Form under Document Design Assemblies owns headings, state
callouts, checkbox syntax, Task separators, completed-task strike-through,
durability warning presentation, and source ordering.

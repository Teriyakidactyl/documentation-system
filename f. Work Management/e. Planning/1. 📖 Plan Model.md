# 📖 Plan Model

## 1. Plan

A Plan is a standalone Work Object whose primary job is to coordinate multiple
acceptance boundaries toward one repository outcome.

A Plan normally keeps its executable structure in one Markdown file:

```text
Plan
├── outcome and Plan acceptance boundary
├── constraints
├── Plan-local Tasks
│   └── Steps
├── dependencies and Gates
├── decisions and uncertainty
├── current execution state
└── next action / handoff context
```

A Plan is not a folder of Task files by default. File decomposition is an
exception for work that has become independently stateful outside the Plan.

## 2. Plan-local Task

A Plan-local Task is the ordinary executable unit inside a Plan.

Its required semantic fields are:

```yaml
id: T1
state: ready | active | blocked | review | completed | cancelled
acceptance:
  - <observable completion condition>
```

The ID is local to the Plan. `T1` in `P004` is distinct from `T1` in
`P005` and is not repository Work ID `T001`.

Use `P004:T1` only when a reference must cross the immediate Plan boundary.

A Plan-local Task owns one acceptance boundary. Do not split a cohesive Task
merely to expose every action as a graph node.

## 3. Step

A Step is an action required inside a Plan-local Task acceptance boundary.

Every Step has checkbox completion state. Steps do not carry independent
`state:` values, dispositions, Work IDs, or files.

If execution needs independent blocking, review, handoff, cancellation, or
acceptance, promote the item to a Plan-local Task rather than extending Step
state.

The Plan Document Form owns the Markdown checkbox syntax and visual
representation.

## 4. Task state

Plan-local Task state means:

| State | Meaning |
|---|---|
| `ready` | The acceptance boundary is understood and starting conditions are satisfied. |
| `active` | The Task currently holds execution attention. |
| `blocked` | A named unsatisfied condition prevents progress. |
| `review` | Execution is materially complete and a review or validation condition remains. |
| `completed` | The Task acceptance boundary is satisfied. |
| `cancelled` | The Plan no longer intends to satisfy the original Task acceptance boundary. |

The explicit state is canonical. Callouts, strike-through, and other Markdown
treatment are Plan Form representations of that state.

## 5. Relation

A Plan relation is a named edge between Plan-local Tasks, standalone Work
Objects, Gates, or relevant conditions.

A minimal dependency can be expressed semantically as:

```yaml
from: T1
to: T2
type: requires
gate: G1
```

Use explicit relations only when the edge affects safe execution, handoff, or
completion. Simple Steps within one Task do not need graph edges.

## 6. Gate

A Gate states the minimum observable condition that permits a downstream Task
to start or close.

```yaml
G1:
  condition: Work Object vocabulary is stable enough for serialization.
  evidence: Work Model object-kind and state tables.
  threshold: Every serialized field used by T2 has one defined meaning.
```

A dependency without a meaningful threshold is ordering preference rather than
a hard execution Gate.

Every cyclic dependency declares an exit Gate.

## 7. Validation timing

A validation activity or Gate can be:

- `immediate` after producing work;
- `deferred` until dependent context exists;
- `terminal` at Plan outcome acceptance; or
- `continuous` while upstream work proceeds.

A terminal property that cannot be added safely after the fact requires a
continuous upstream check.

## 8. Commitment cost

`reversible` Tasks are inexpensive to revisit. `stabilizing` Tasks reduce
uncertainty and should fire when sufficient inputs exist. `locking` Tasks make
later change expensive and require strong upstream Gates.

Commitment cost is planning information. It is not Task priority.

## 9. Execution frontier

The frontier is derived:

```text
Task state is not completed/cancelled
AND Task can execute
AND all hard prerequisite Gates are satisfied
AND no active blocking condition exists
```

A Plan may record a frontier snapshot for handoff, but the Plan must contain
enough current state to recompute it.

## 10. Single-file default

Plan-local Tasks and their Steps remain in the Plan file.

Do not allocate repository-global Task IDs for ordinary Plan Tasks. Do not
materialize ten Task files merely because the Plan has ten executable Tasks.

A Plan can reference standalone Work Objects where independently managed work
already exists or is deliberately promoted.

## 11. Promotion to standalone Task

Promote a Plan-local Task when it needs durable independence from the Plan, such
as:

- independent handoff or retrieval;
- lifecycle that can outlive or move between Plans;
- acceptance or review owned outside the Plan;
- reuse by several Plans or Work Objects; or
- independent blocking/close-out that must remain queryable without loading the
  Plan.

Promotion allocates a new standalone `T###` Work ID through repository
automation.

After promotion, the Plan-local Task records the target standalone Task and
stops carrying duplicate executable state. The standalone Task becomes
authoritative for its own lifecycle.

## 12. Representation boundary

This Reference owns Plan semantics, not Markdown layout.

When a Plan is recorded as Markdown, apply the Plan Document Form under Document
Design Assemblies. That Form owns headings, state callouts, checkbox syntax,
Task separators, completed-task strike-through, and source ordering.

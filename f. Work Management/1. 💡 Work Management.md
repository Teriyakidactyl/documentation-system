# 💡 Work Management

Repository work is changing coordination state around artifacts whose authority
belongs elsewhere. Work Management exists so an agent can discover what needs
attention, what is safe to do next, and why work stopped without reconstructing
that state from conversation history.

## 1. Work state is not product authority

A Task that says “rename the parser API” does not make that rename correct.
The governing technical authority decides what the implementation must become;
the Task records that changing it is work.

The same boundary applies to Plans, Investigations, Decisions, and Handoffs.
When work discovers a conclusion future actors must rely on, promote that
conclusion into the controlled authority that owns the subject.

## 2. Records are sources, not lifecycle state

Feedback, Issue, Fault Record, Research, and other retained information can
explain why work exists without becoming Work Objects merely because action
follows.

The distinction is:

```text
Record
    → preserves an observation, condition, request, finding, evidence, or provenance

Work Object
    → carries executable, coordinating, investigative, decision, or continuation state
```

A Record may derive, concern, evidence, or motivate a Task or Plan. Preserve
that relationship explicitly when it matters; do not add Task lifecycle fields
to the Record.

## 3. Work is a graph before it is a queue

Filesystem containment groups information for retrieval but does not replace
meaningful edges.

Examples:

```text
Issue Record ──derives────────→ Task
Fault Record ──remediated-by──→ Task
Plan ─────────coordinates─────→ Task
Task ─────────requires────────→ Task
Task ─────────validates───────→ controlled artifact
Feedback ─────concerns────────→ Plan
```

The actionable queue is a projection of this graph. Priority orders otherwise
actionable work; it cannot override an unsatisfied Gate.

## 4. Task and Plan are different coordination scales

A standalone Task is the smallest independently executable Work Object whose
lifecycle must survive outside a Plan.

A Plan coordinates several acceptance boundaries when dependencies, Gates,
ordering, validation timing, uncertainty, or durable multi-agent resumability
justify explicit planning.

A Plan is not a mandatory parent for every Task.

## 5. Durable state precedes conversational continuity

An executing agent may not retain prior conversation. Active Tasks and Plans
must preserve enough durable current state to resume without it.

For Plans, durability is established before the Plan becomes the execution
continuity source. Repository-local Plans are registered and stored under
`.project/Planning/Plans/` when Work automation is available.

## 6. State and placement answer different questions

Work state answers what can happen now. Placement answers which Work Management
responsibility stores the object.

The stable project containment layer is:

```text
.project/
├── Records/   ← retained non-work collector
├── Planning/
├── Execution/
└── Archive/
```

State changes do not create status directories. Archive movement follows an
explicit cold-retention decision.

## 7. Execution must account for the current harness

The Plan author and later executor may have different harness capabilities.
Before entering an execution frontier, an executor reassesses materially
relevant retrieval limits, persistence, code execution, network/external calls,
permissions, and specialized tools.

Only capability facts that change execution, blocking, validation, handoff, or
acceptance become durable work context.

## 8. Close-out preserves why attention ended

Closed work carries an explicit disposition rather than an opaque done state.
Completion, cancellation, rejection, duplication, supersession, conversion, and
deferral express different reasons active attention ended.

Close-out promotes surviving current truth to its proper owner, preserves
required traceability, selects active or cold retention, and recomputes the
execution frontier.

Deletion is not the default close-out operation.

# 💡 Work Management

Repository work is a changing coordination state around artifacts whose own
authority belongs elsewhere. Work Management exists so an agent can discover
what needs attention, why it matters, what is safe to do next, and what happened
when work stopped, without reconstructing that state from conversation history.

## 1. Work state is not product authority

A Task that says "rename the parser API" does not make that rename correct.
The governing Software Design or current Architecture authority decides what
the implementation must become. The Task records that changing it is work.

The same boundary applies to every work object. An Issue can identify a gap
without becoming the rule that closes the gap. A Fault can retain evidence and
causal understanding without becoming current technical authority. A Plan can
order documentation work without owning the resulting documentation semantics.

Work Management therefore owns the invariant:

```text
work object
    → records why, whether, and how repository work proceeds

governed artifact
    → records what is currently true in its own domain
```

When work discovers a conclusion that future actors must rely on, promote that
conclusion into the controlled authority that owns the subject. Do not leave
current truth available only through a Task, Plan, Fault, or handoff.

## 2. Work is a graph before it is a queue

A queue answers what can be considered next. It does not capture why one item
is blocked, what another item owes it, which fault produced remediation work,
or whether several tasks can proceed independently.

Work Management therefore treats explicit relationships as first-class:

```text
Issue ──raises────────────→ Task
Fault ──remediated-by─────→ Task
Plan  ──coordinates───────→ Task
Task  ──requires──────────→ Task
Task  ──validated-by──────→ Validation
Feedback ──concerns───────→ Plan
```

Filesystem containment groups records for retrieval. It does not replace these
edges.

The actionable queue is a projection of this graph. An incomplete Task belongs
to the execution frontier when its prerequisites and gates are satisfied. A
priority field may order otherwise actionable work, but it must not pretend an
unsatisfied dependency is merely low priority.

## 3. Work enters before it becomes a Task

Repository signals differ in what they assert.

An Idea records a possibility. Feedback records an observation, reaction,
request, or critique concerning another subject. An Issue records a condition
that requires attention. A Fault records an observed failure and the evidence
needed to understand or prevent recurrence.

None of those signals must become a Task immediately. Intake and shaping can
reject, defer, merge, relate, investigate, or promote them. This preserves the
difference between "something deserves thought" and "this executable unit is
ready to be done."

A Task is the smallest independently executable Work Object. A Plan is not a
mandatory parent. Creating one Task for one bounded outcome is a complete and
valid Work Management operation.

## 4. Plans coordinate rather than contain truth

A Plan coordinates an outcome that needs more structure than one Task. It can
contain or reference Tasks, investigations, decisions, validations, milestones,
external conditions, and other nodes required to make execution resumable.

A useful Plan exposes:

- the intended outcome and acceptance boundary;
- the nodes needed to reach it;
- explicit relations among those nodes;
- gates that state what an upstream result must provide before downstream work
  is safe;
- the current execution frontier;
- unresolved decisions and uncertainty; and
- enough state and handoff context for another agent to continue.

A dependency edge should state what one node owes another. "A before B" is
weaker than "A must establish the stable Work Object vocabulary before B can
specify task serialization." The latter is an executable gate.

## 5. State and placement answer different questions

Work state answers what can happen to an object now. Placement answers which
repository management responsibility stores it.

A Task remains under the Execution responsibility while moving through states
such as captured, ready, active, blocked, review, and closed. Moving a file
between status directories for every state change would make paths compete with
metadata for authority and would churn references.

The stable target-repository storage layer is:

```text
.project/
├── Intake/
├── Planning/
├── Execution/
└── Archive/
```

Optional object-kind folders can fan out beneath those responsibilities.
Close-Out is a lifecycle operation, not a required top-level storage branch.

## 6. Handoffs are part of correctness

An amnesiac agent cannot rely on prior conversational state. Every active Task
or Plan must therefore preserve enough current state to resume from the
repository alone.

The minimum handoff answers:

- what changed;
- what is true now;
- what the next action is;
- what blocks that action, if anything; and
- which governing authority or evidence the next actor must consult.

A handoff should summarize current execution context rather than reproduce the
whole history. Durable rationale that has an independent future job belongs in
its appropriate decision, research, fault, or authoritative artifact.

## 7. Close-out preserves why attention ended

A Work Object leaves the active frontier for more than one reason. Completion,
cancellation, rejection, duplication, supersession, conversion, and deferral
must not collapse into one opaque `done` state.

Close-Out assigns a disposition, records any surviving relationship, confirms
that current truth has been promoted to its proper owner, and selects retention.
Recent or operationally useful closed work can remain in its responsibility
store with `state: closed`. Cold material can move to `.project/Archive/`
without changing its durable Work ID or controlled UID.

Deletion is not the default close-out operation. A small retained record of why
work left active attention prevents later agents from treating deliberate
closure as forgotten work.

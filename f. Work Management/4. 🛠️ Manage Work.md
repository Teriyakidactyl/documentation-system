# 🛠️ Manage Work

## 1. Start from the source condition

Work may begin from a user request, a retained Record, another Work Object, a
decision, or an observed repository condition.

Preserve the source information at its proper owner. Do not convert Feedback,
Issue, Fault Record, Research, or another Record into executable state merely to
make action possible.

When the source requires action, create or select the smallest Work Object whose
acceptance boundary can carry that action.

## 2. Choose Task or Plan

Use a standalone Task for one independently executable outcome whose lifecycle
must survive outside any Plan.

Use a Plan when multiple acceptance boundaries require coordination,
dependencies, Gates, ordering, validation timing, or durable multi-agent
resumability.

Apply the corresponding Document Form for representation. Work Management owns
identity, storage, lifecycle, and relations; the Form owns the Markdown source
contract.

## 3. Establish identity and actionability

Use repository automation for standalone Work ID allocation when that capability
exists. Do not manually choose a supposedly next ID that automation owns.

Set work to `ready` only when its acceptance boundary is understood and every
starting prerequisite is satisfied. Otherwise keep it captured or blocked and
name the missing condition.

## 4. Reassess the execution environment

Before acting, apply the Work Form capability prompt: confirm the current
harness can safely perform and validate the next work.

A later executor may have different retrieval limits, persistence, code
execution, network access, connectors, permissions, or specialized tools than
the author. Record a limitation only when it changes execution, blocking,
validation, handoff, or acceptance.

## 5. Select from the execution frontier

Choose incomplete work whose prerequisites and Gates are satisfied. Use priority
only to order work already in the frontier.

Read the current state, next action, governing authority, and evidence required
for that action before mutation.

## 6. Execute and maintain current truth

Mark selected work active when execution begins. Update current state when a
material repository or external-state change would alter what a resuming agent
should do.

Keep working decisions in the Work Object only while they remain working
information. Promote current technical or documentation truth into the
controlled artifact that owns the subject.

## 7. Handle blocking and review

When progress cannot continue, set `blocked` and record the unsatisfied
condition, responsible Work Object or external event when known, evidence, and
the next check or action.

Use `review` only when primary execution is materially complete and a declared
review or Validation Gate still determines acceptance.

## 8. Preserve resumability and handoff

Before interruption or transfer, make the Work Object answer:

```text
Changed:
Current state:
Next action:
Blocked by:
Governing authority:
Evidence:
```

Omit genuinely empty optional fields. Create a separate Handoff Work Object only
when the continuation package has independent recipient, lifecycle, or retrieval
needs.

A resuming agent treats durable repository state as the continuity source rather
than prior conversation.

## 9. Close active attention

When acceptance is satisfied, or work should intentionally stop for another
reason, set `state: closed` and exactly one canonical disposition.

For duplicate, superseded, or converted work, record the surviving target. For
deferred work, record the condition that can make reconsideration appropriate.

Do not use close-out to hide unresolved work.

## 10. Promote surviving truth and preserve traceability

Before completion, ensure every rule, architecture fact, documentation fact,
code behavior, or other current truth produced by the work is recorded at its
proper semantic owner.

Retain the minimum facts needed to explain why active attention ended, which
acceptance conditions were met, which Work Objects survive, what authority
changed, and what evidence matters.

## 11. Select retention and recompute the frontier

Use active retention when recent closure or nearby work makes the record useful
in its normal store. Use cold retention when the record has legitimate
historical value but no normal operating role, preserving identity and
disposition under Archive.

Remove closed work from actionable projections and recompute downstream Gates
and the execution frontier.

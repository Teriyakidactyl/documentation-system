# 🛠️ Plan Work

## 1. Establish durable Plan state

Before the Plan becomes the execution continuity source, persist it somewhere
the executing agent can retrieve after interruption, handoff, or conversation
compaction.

Use repository Work Management storage and identity mechanisms when available.
When the current harness cannot use them, record the durable fallback and the
limitation instead of inventing repository identity manually.

## 2. Prepare before decomposition

Do not decompose from the requested outcome alone.

1. assess the authoring harness capabilities and material limits;
2. read applicable Work Management guidance;
3. identify domains and operations implied by the outcome;
4. read their governing guidance according to each directive;
5. inspect enough current state to trace currently discoverable implementation,
   validation, handoff, and completion implications; and
6. repeat guidance/capability discovery when new governed concerns appear.

This preparation is plan-authoring work, not automatically planned work.

## 3. State the outcome and acceptance boundary

Write one observable repository outcome, the conditions that make the Plan
complete, and binding constraints.

When preparation reveals additional work required for that outcome, represent
it as discovered planned work.

## 4. Use the Plan Document Form

Apply the Plan Form under Document Design Assemblies when recording the Plan as
Markdown. Work Management determines meaning; the Form determines source
representation.

## 5. Establish Plan-local Tasks

Create one Plan-local Task for each independently meaningful acceptance
boundary. Use compact Plan-local IDs. Do not create standalone Task files for
ordinary Plan Tasks.

## 6. Add Steps

Break a Task into Steps only when actions help execution or handoff. Steps stay
inside the Task acceptance boundary. The Plan Form owns checkbox syntax.

## 7. Establish dependencies and Gates

For each meaningful dependency, state the observable upstream condition required
by downstream work. Reject dependencies whose only meaning is “A before B”.

## 8. Add complexity only when needed

Use the least structure that makes execution deterministic enough: acceptance
boundaries, Steps, explicit relations, Gates, then validation timing/cycles/
commitment cost only when the problem requires them.

## 9. Promote work only when independence appears

When a Plan-local Task needs lifecycle or retrieval independence, register a
standalone Task through repository automation and stop duplicate executable
state in the Plan.

## 10. Record the executor capability check

Preserve an early instruction requiring each executing agent to assess its own
materially relevant harness capabilities before entering the execution
frontier.

Do not treat the Plan author’s tools as durable execution facts. Record a
specific limitation only when it affects execution, blocking, validation,
handoff, or acceptance.

## 11. Compute the execution frontier

Identify incomplete work whose prerequisites and Gates are satisfied and which
has no active blocker. Keep priority separate from dependency.

## 12. Write resumable current state

Record the current frontier, active work, blocked work and unmet Gates,
unresolved decisions, changed assumptions, next action, and required authority
or evidence.

Another agent must be able to continue from durable Plan state without prior
conversation.

## 13. Maintain current execution truth

Update Task state, Steps, Gates, acceptance boundaries, and current state as
work changes. Newly discovered guidance or capability constraints that
materially change the work require Plan revision before affected execution
continues.

## 14. Close the Plan

When the outcome is satisfied or coordinated work intentionally ends, apply the
generic Work close-out semantics and ensure surviving current truth has moved to
its proper owner.

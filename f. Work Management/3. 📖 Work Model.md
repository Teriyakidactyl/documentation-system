# 📖 Work Model

## 1. Work Object

A **Work Object** is a repository-local record whose primary job is to carry
mutable or retained work state.

Every standalone Work Object has:

| Field | Requirement |
|---|---|
| `uid` | Controlled durable artifact identity minted by Organizing. |
| `description` | Canonical retrieval description required by Document Control. |
| `work.id` | Human-usable stable Work ID unique within `.project/`. |
| `work.type` | Work Object kind. |
| `work.state` | Current lifecycle state when the type is stateful. |
| `work.updated` | Date or timestamp of the latest material state change. |

A Work ID survives rename, movement to Archive, and attachment to a Plan.
The controlled `uid` identifies the documented artifact; `work.id` identifies
the Work Management object in work-facing relationships.

## 2. Work Object kinds

| Kind | Meaning | Typical home |
|---|---|---|
| `idea` | Possibility worth retaining before commitment to action. | `.project/Intake/Ideas/` |
| `feedback` | Observation, reaction, suggestion, critique, or request concerning a subject. | `.project/Intake/Feedback/` |
| `issue` | Recognized condition requiring attention or disposition. | `.project/Intake/Issues/` |
| `fault` | Observed failure plus the work-facing evidence and causal state needed for remediation or recurrence control. | `.project/Intake/Faults/` |
| `investigation` | Bounded work to reduce uncertainty before another commitment can safely occur. | `.project/Planning/Investigations/` |
| `decision` | Work-facing choice that constrains a Plan or Task. Durable architecture decision provenance remains an ADR when its own Form applies. | `.project/Planning/Decisions/` |
| `plan` | Coordinated graph of nodes, relations, gates, state, and acceptance conditions for an outcome. | `.project/Planning/Plans/` |
| `task` | Smallest independently executable unit of repository work. | `.project/Execution/Tasks/` |
| `handoff` | Explicit continuation package when a separate record is justified. | `.project/Execution/Handoffs/` |
| `workset` | Optional grouping identity for several Work Objects that share one durable initiative without requiring one Plan to contain all work. | responsibility selected by its active purpose |

A deliverable is normally an output relationship, not a Work Object kind.
Draft is normally artifact maturity, not a Task state. Review and Validation
are activities or gates unless their execution needs an independently tracked
Task.

## 3. Lifecycle state

The common actionable state vocabulary is:

| State | Meaning |
|---|---|
| `captured` | Recorded, but actionability has not been established. |
| `ready` | Acceptance conditions are understood and all prerequisites for starting are satisfied. |
| `active` | Work is currently being executed. |
| `blocked` | Work is incomplete and a named unsatisfied condition prevents progress. |
| `review` | Primary execution is complete and a required review or validation gate remains. |
| `closed` | The object no longer competes for active execution attention and has a disposition. |

Types may use a strict subset. An Idea can remain captured until shaped. A Plan
can be active while several coordinated Tasks are in different states.

State is canonical metadata. A directory name must not independently claim the
same lifecycle fact.

## 4. Disposition

A closed Work Object records one disposition:

| Disposition | Meaning |
|---|---|
| `completed` | Acceptance conditions were satisfied. |
| `cancelled` | Work was intentionally stopped without satisfying the original acceptance condition. |
| `rejected` | The proposed work was considered and declined. |
| `duplicate` | Another Work Object owns the surviving work; record the relation. |
| `superseded` | A newer object or approach replaces this one; record the successor. |
| `converted` | This object intentionally became another work kind or object; record the target. |
| `deferred` | Active attention ended until a named future condition or decision reopens consideration. |

`closed` without a disposition is incomplete close-out.

## 5. Relation

Relations are named graph edges. Prefer the smallest vocabulary that preserves
the decision an executor needs.

| Relation | Meaning |
|---|---|
| `concerns` | Source object is about the target. |
| `derives-from` | Source exists because of the target input or event. |
| `requires` | Source cannot safely complete before the target supplies a named condition. |
| `enables` | Source output makes the target actionable without making it mandatory. |
| `blocks` | Source currently prevents target progress. |
| `coordinates` | A Plan or workset organizes the target. |
| `produces` | Work creates or materially establishes the target output. |
| `validates` | Source checks a declared property of the target. |
| `resolves` | Source closes the attention condition represented by the target. |
| `remediates` | Source corrects or mitigates a Fault. |
| `supersedes` | Source replaces target as the current surviving work representation. |
| `duplicates` | Source and target represent the same work; one survives. |

A relation can carry a gate. Containment must not substitute for a relation
whose identity affects execution.

## 6. Gate

A Gate is a checkable condition that controls whether a downstream node may
fire or close.

A dependency Gate records:

```yaml
gate:
  condition: <observable condition>
  evidence: <where the executor can verify it>
  threshold: <minimum sufficient state>
```

For `requires`, the threshold states what the upstream node owes the
downstream node. "T001 complete" is weaker than "T001 has established the
canonical field vocabulary used by T002."

A cyclic planning relation additionally needs an exit Gate. "Iterate until
stable" is not sufficient unless stable is operationally defined.

## 7. Priority and execution frontier

Priority orders otherwise actionable work. It does not override an unsatisfied
Gate.

The **execution frontier** is the derived set of incomplete executable nodes
whose prerequisites and gates are currently satisfied. Queue, ready list,
critical path, and blocked list are projections over canonical Work Objects and
Relations rather than separately maintained sources of truth.

## 8. Artifact maturity

Artifact maturity is independent from work lifecycle.

```yaml
artifact:
  maturity: draft
```

A Task may be active while its output is draft. A closed Task may leave a
draft proposal if its disposition is rejected or superseded. Do not encode
artifact maturity as Task state.

## 9. Retention

`retention: active` means the Work Object remains in its responsibility store.
`retention: cold` means Close-Out has selected archival storage under
`.project/Archive/`.

Moving to Archive changes retrieval treatment, not identity or historical
disposition.

# 📖 Work Model

## 1. Work Object

A **Work Object** is a repository-local record whose primary job is to carry
mutable or retained work state independently of conversational context.

Every standalone Work Object has:

| Field | Requirement |
|---|---|
| `uid` | Controlled durable artifact identity minted and maintained by repository automation when the host corpus uses controlled UIDs. |
| `description` | Canonical retrieval description required by Document Control. |
| `work.id` | Human-usable stable Work ID unique across the complete `.project/` tree, including Archive. |
| `work.type` | Work Object kind. |
| `work.state` | Current lifecycle state when the type is stateful. |
| `work.updated` | Date or timestamp of the latest material state change. |

A Work ID survives rename, movement to Archive, and attachment to a Plan.
Archived or deleted historical numbers are never recycled. The controlled
`uid` identifies the documented artifact; `work.id` identifies the
standalone Work Management object in work-facing relationships.

Plan-local Task IDs are not `work.id` values.

## 2. Work Object kinds

| Kind | Meaning | Typical home |
|---|---|---|
| `idea` | Possibility worth retaining before commitment to action. | `.project/Intake/Ideas/` |
| `feedback` | Observation, reaction, suggestion, critique, or request concerning a subject. | `.project/Intake/Feedback/` |
| `issue` | Recognized condition requiring attention or disposition. | `.project/Intake/Issues/` |
| `fault` | Observed failure plus the work-facing evidence and causal state needed for remediation or recurrence control. | `.project/Intake/Faults/` |
| `investigation` | Bounded work to reduce uncertainty before another commitment can safely occur. | `.project/Planning/Investigations/` |
| `decision` | Work-facing choice that constrains a Plan or standalone Task. Durable architecture decision provenance remains an ADR when its own Form applies. | `.project/Planning/Decisions/` |
| `plan` | Coordinated execution model for one outcome, normally containing Plan-local Tasks, Steps, relations, gates, state, and acceptance conditions in one file. | `.project/Planning/Plans/` |
| `task` | Independently executable repository work whose lifecycle and retrieval identity must survive outside any one Plan. | `.project/Execution/Tasks/` |
| `handoff` | Explicit continuation package when a separate record is justified. | `.project/Execution/Handoffs/` |

A deliverable is normally an output relationship, not a Work Object kind.
Draft is normally artifact maturity, not Task state. Review and Validation are
activities or gates unless their execution needs an independently tracked
standalone Task.

## 3. Standalone Task

A **standalone Task** is a `task` Work Object with repository-global identity,
for example `T043`.

Create a standalone Task when the executable outcome must be retrieved,
resumed, handed off, blocked, reviewed, closed, or related independently of a
single Plan. A standalone Task can exist without any Plan.

Do not create a standalone Task file merely because a Plan contains executable
work. Ordinary Plan execution belongs to Plan-local Tasks.

## 4. Plan-local Task

A **Plan-local Task** is an executable acceptance boundary owned by one Plan.
It is not a standalone Work Object and does not receive a repository-global
`T###` ID.

Use a compact Plan-local identifier such as `T1`, `T2`, and `T3`. Its
qualified identity, when a reference outside the immediate Plan is unavoidable,
is the Plan ID plus local ID, for example `P004:T2`.

A Plan-local Task has:

- one independently meaningful acceptance boundary;
- a Plan-local state;
- optional prerequisite relations or Gates; and
- zero or more Steps.

Promote a Plan-local Task to a standalone Task only when it needs durable
lifecycle or retrieval independence from the Plan. Promotion allocates a new
repository-global Work ID and records that the Plan-local Task was promoted to
that Work Object; it does not pretend the local ID was already a global ID.

## 5. Step

A **Step** is an execution action inside one Task acceptance boundary.

A Step has no independent lifecycle identity. Its completion state is the
Markdown checkbox state defined by the Plan Document Form:

```markdown
- [ ] incomplete
- [x] complete
```

If an item needs independent blocking, handoff, cancellation, review, or
acceptance, represent it as a Plan-local Task or standalone Task rather than
adding a second lifecycle model to a Step.

## 6. Lifecycle state

The common standalone Work Object state vocabulary is:

| State | Meaning |
|---|---|
| `captured` | Recorded, but actionability has not been established. |
| `ready` | Acceptance conditions are understood and all prerequisites for starting are satisfied. |
| `active` | Work is currently being executed. |
| `blocked` | Work is incomplete and a named unsatisfied condition prevents progress. |
| `review` | Primary execution is complete and a required review or validation gate remains. |
| `closed` | The object no longer competes for active execution attention and has a disposition. |

Plan-local Tasks use the narrower planning vocabulary defined by the Plan Model.
Their state is owned inside the Plan rather than duplicated as standalone Work
Object metadata.

State is canonical information. A directory name or visual Markdown treatment
must not independently claim a contradictory lifecycle fact.

## 7. Disposition

A closed standalone Work Object records one disposition:

| Disposition | Meaning |
|---|---|
| `completed` | Acceptance conditions were satisfied. |
| `cancelled` | Work was intentionally stopped without satisfying the original acceptance condition. |
| `rejected` | The proposed work was considered and declined. |
| `duplicate` | Another Work Object owns the surviving work; record the relation. |
| `superseded` | A newer object or approach replaces this one; record the successor. |
| `converted` | This object intentionally became another work kind or object; record the target. |
| `deferred` | Active attention ended until a named future condition or decision reopens consideration. |

`closed` without a disposition is incomplete close-out.

## 8. Relation

Relations are named graph edges between standalone Work Objects. Prefer the
smallest vocabulary that preserves the decision an executor needs.

| Relation | Meaning |
|---|---|
| `concerns` | Source object is about the target. |
| `derives-from` | Source exists because of the target input or event. |
| `requires` | Source cannot safely complete before the target supplies a named condition. |
| `enables` | Source output makes the target actionable without making it mandatory. |
| `blocks` | Source currently prevents target progress. |
| `coordinates` | A Plan or workset organizes a standalone target. |
| `produces` | Work creates or materially establishes the target output. |
| `validates` | Source checks a declared property of the target. |
| `resolves` | Source closes the attention condition represented by the target. |
| `remediates` | Source corrects or mitigates a Fault. |
| `supersedes` | Source replaces target as the current surviving work representation. |
| `duplicates` | Source and target represent the same work; one survives. |

Plan-local dependencies are owned by the Plan Model and need not be promoted to
global Work Object relations.

## 9. Gate

A Gate is a checkable condition that controls whether downstream work may fire
or close.

A dependency Gate records:

```yaml
gate:
  condition: <observable condition>
  evidence: <where the executor can verify it>
  threshold: <minimum sufficient state>
```

For `requires`, the threshold states what the upstream work owes the
downstream work. "T1 complete" is weaker than "T1 has established the canonical
field vocabulary used by T2."

A cyclic planning relation additionally needs an exit Gate. "Iterate until
stable" is not sufficient unless stable is operationally defined.

## 10. Priority and execution frontier

Priority orders otherwise actionable work. It does not override an unsatisfied
Gate.

The **execution frontier** is the derived set of incomplete executable work
whose prerequisites and gates are currently satisfied. Queue, ready list,
critical path, and blocked list are projections over canonical Work Objects and
Plan state rather than separately maintained sources of truth.

## 11. Artifact maturity

Artifact maturity is independent from work lifecycle.

```yaml
artifact:
  maturity: draft
```

A Task may be active while its output is draft. A closed Task may leave a draft
proposal if its disposition is rejected or superseded. Do not encode artifact
maturity as Task state.

## 12. Retention

`retention: active` means the Work Object remains in its responsibility store.
`retention: cold` means Close-Out has selected archival storage under
`.project/Archive/`.

Moving to Archive changes retrieval treatment, not identity or historical
disposition.

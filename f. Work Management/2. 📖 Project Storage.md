# 📖 Project Storage

## 1. Storage root

A repository that owns its Work Management state stores it beneath the reserved
`.project/` sideband at repository root.

The sideband supplies four control benefits:

1. one deterministic location for resumable repository work;
2. separation of mutable working information from current product authority;
3. address-opaque storage that does not enter ordinary Documentation System
   indexes; and
4. automatic omission from this repository's dot-prefixed `latest`
   distribution projection.

`.project/` is not hidden authority. Rules that a user must rely on belong in
the controlled artifact that owns their subject.

## 2. Responsibility layer

The stable first layer is:

```text
.project/
├── README.md
├── Intake/
├── Planning/
├── Execution/
└── Archive/
```

The siblings answer one question: which Work Management responsibility owns the
record's present storage role?

- **Intake** stores signals being retained, triaged, investigated, or promoted
  into committed work.
- **Planning** stores coordination structures and planning-stage work whose
  primary job is to decide or structure execution.
- **Execution** stores independently executable work and explicit continuation
  material.
- **Archive** stores cold Work Objects after Close-Out selects archival
  retention.

Close-Out is not a fifth storage responsibility. It is the operation that
changes active attention, disposition, and retention.

## 3. Optional object-kind folders

Create object-kind folders only when at least two records or a recurring
retrieval need justify the grouping.

Recognized examples are:

```text
.project/
├── Intake/
│   ├── Ideas/
│   ├── Feedback/
│   ├── Issues/
│   └── Faults/
├── Planning/
│   ├── Plans/
│   ├── Investigations/
│   └── Decisions/
├── Execution/
│   ├── Tasks/
│   └── Handoffs/
└── Archive/
```

The list is not a requirement to create empty directories. A repository can
begin with only `.project/Execution/Tasks/T001 ...md`.

## 4. Stable placement

Normal lifecycle changes do not move an object between status folders. State is
stored in the Work Object.

A Task remains in `Execution/Tasks/` while captured, ready, active, blocked,
review, or recently closed. A Plan remains in `Planning/Plans/` while its
coordinated nodes advance.

Move an object to Archive only when Close-Out explicitly sets
`retention: cold`. Preserve `uid`, `work.id`, disposition, and surviving
relations.

## 5. Controlled sideband behavior

Document Control recognizes `.project` as a controlled sideband. Organizing
descends into metadata-bearing supported artifacts, mints missing UIDs, and
validates controlled metadata. Descendants receive no Documentation System
address and do not enter generated indexes.

Folder-prefix normalization does not rename the sideband or its descendants.
Work Management, not the Documentation System address hierarchy, owns their
internal names and Work IDs.

Agents retrieve `.project` when the user asks to manage or resume repository
work, when an active task requires its tracked state, or when the repository
entry guidance routes into Work Management. Closed cold history should not be
loaded merely because it exists.

## 6. Naming

Standalone Work Objects begin with their Work ID followed by a concise title:

```text
T001 Fix broken README link.md
P003 Replace parser surface.md
F007 Truncated traversal.md
```

The Work ID is stable. Renaming the title portion does not change identity.

Use type-appropriate prefixes consistently within one repository. The default
prefixes are `I` Idea, `FB` Feedback, `IS` Issue, `F` Fault, `R`
Investigation, `D` work-facing Decision, `P` Plan, `T` Task, and `H`
Handoff.

## 7. Minimal file control envelope

A standalone Task can remain small:

```yaml
---
description: >-
  `Consult when` *task T001 must be resumed or inspected* `to` **recover
  its outcome, current state, and next action**.
work:
  id: T001
  type: task
  state: ready
  updated: 2026-09-25
---
```

Organizing mints `uid`. Do not invent a replacement UID during ordinary work.

The body then needs only the information required by the type. The one-off Task
procedure defines the smallest useful Task body.

## 8. Single-file and multi-file growth

Start with the smallest representation that preserves the Work Model.

One Task:

```text
.project/
└── Execution/
    └── Tasks/
        └── T001 Fix broken README link.md
```

One Plan can keep its nodes in one file when that remains readable. When nodes
need independent execution, handoff, or lifecycle, materialize them as separate
Work Objects and reference their existing IDs.

Decomposition is not migration to a new semantic model. The same IDs and
relations survive the representation change.

## 9. Publication

A consuming repository may choose its own distribution policy, but this
Documentation System's Skill Distribution omits any path with a dot-prefixed
component. Therefore `.project/` and every descendant are absent from
`latest` without an additional exclusion list.

Do not move current Work Management guidance itself under `.project/`.
Guidance belongs in the published Work Management root; mutable instances belong
in the sideband.

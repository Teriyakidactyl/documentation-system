# 📖 Project Storage

## 1. Storage root

A repository that owns its Work Management state stores it beneath the reserved
`.project/` sideband at repository root.

The sideband supplies four control benefits:

1. one deterministic location for resumable repository work;
2. separation of mutable working information from current product authority;
3. address-opaque storage that does not enter ordinary Documentation System
   indexes; and
4. omission from this repository's dot-prefixed `latest` distribution
   projection.

`.project/` is not hidden authority. Rules that a user must rely on belong in
the controlled artifact that owns their subject.

## 2. Canonical project skeleton

The Work Management setup procedure materializes this complete skeleton:

```text
.project/
├── README.md
├── metrics.json
├── Intake/
│   ├── Ideas/
│   ├── Feedback/
│   ├── Issues/
│   └── Faults/
├── Planning/
│   ├── Plans/
│   ├── Investigations/
│   └── Decisions/
├── Execution/
│   ├── Tasks/
│   └── Handoffs/
└── Archive/
    ├── Intake/
    │   ├── Ideas/
    │   ├── Feedback/
    │   ├── Issues/
    │   └── Faults/
    ├── Planning/
    │   ├── Plans/
    │   ├── Investigations/
    │   └── Decisions/
    └── Execution/
        ├── Tasks/
        └── Handoffs/
```

Git does not retain empty directories. Repository setup may therefore use
`.gitkeep` anchors in empty leaves. Those anchors carry no Work Management
semantics.

## 3. Responsibility layer

The stable first layer remains Intake, Planning, Execution, and Archive.

- **Intake** stores signals being retained, triaged, investigated, or promoted
  into committed work.
- **Planning** stores Plans and other work whose primary job is to decide or
  coordinate execution.
- **Execution** stores independently executable standalone Tasks and explicit
  continuation material.
- **Archive** stores cold Work Objects after Close-Out selects archival
  retention.

Close-Out is not a fifth storage responsibility. It is the operation that
changes active attention, disposition, and retention.

Object-kind folders organize retrieval. They do not encode lifecycle status.

## 4. Stable placement

Normal lifecycle changes do not move an object between status folders. State is
stored in the Work Object or, for Plan-local Tasks, in the Plan.

A standalone Task remains in `Execution/Tasks/` while captured, ready, active,
blocked, review, or recently closed. A Plan remains in `Planning/Plans/` while
its local Tasks advance.

Move a standalone Work Object to Archive only when Close-Out explicitly sets
`retention: cold`. Preserve `uid`, `work.id`, disposition, and surviving
relations.

## 5. Controlled sideband behavior

Document Control recognizes `.project` as a controlled sideband. Repository
automation may descend into metadata-bearing supported artifacts, mint missing
controlled UIDs, and validate Work Management metadata.

Descendants receive no Documentation System address and do not enter generated
indexes.

Folder-prefix normalization does not rename the sideband or its descendants.
Work Management, not the Documentation System address hierarchy, owns their
internal names and Work IDs.

Agents retrieve `.project` when the user asks to manage or resume repository
work, when active work requires tracked state, or when repository guidance
routes into Work Management. Closed cold history should not be loaded merely
because it exists.

## 6. Work ID allocator metrics

`.project/metrics.json` is repository-automation operational state.

Version 1 records the next standalone Work ID number for each recognized kind:

```json
{
  "version": 1,
  "ids": {
    "idea": 1,
    "feedback": 1,
    "issue": 1,
    "fault": 1,
    "investigation": 1,
    "decision": 1,
    "plan": 3,
    "task": 1,
    "handoff": 1
  }
}
```

The counter is a convenience for monotonic allocation, not proof that an ID is
unused. Repository automation validates allocated IDs against the complete
active and archived `.project/` tree.

The next counter for a kind must always exceed every previously allocated
numeric value for that kind. Gaps remain gaps. Archive, close-out, deletion, or
renaming does not permit reuse.

Derived counts may be added later when they have a consumer, but they remain
reconstructible projections rather than semantic authority.

## 7. Naming

Standalone Work Objects begin with their Work ID followed by a concise title:

```text
T001 Fix broken README link.md
P003 Replace parser surface.md
F007 Truncated traversal.md
```

The Work ID is stable. Renaming the title portion does not change identity.

The default standalone prefixes are `I` Idea, `FB` Feedback, `IS` Issue,
`F` Fault, `R` Investigation, `D` work-facing Decision, `P` Plan,
`T` Task, and `H` Handoff.

Plan-local Task identifiers such as `T1` are scoped to their Plan and are not
standalone Work IDs.

## 8. Minimal standalone Task envelope

A standalone Task can remain small:

```yaml
---
description: >-
  `Consult when` *task T001 must be resumed or inspected* `to` **recover
  its outcome, current state, and next action**.
work:
  id: T001
  type: task
  state: ready
  updated: 2026-09-25
---
```

Repository automation mints or maintains `uid` when the host corpus uses
controlled UIDs.

The one-off Task procedure defines the smallest useful Task body.

## 9. Plans and standalone Tasks

A Plan normally keeps its Plan-local Tasks and Steps in one Plan file.

A Plan may reference an existing standalone Task, or promote local work to a
standalone Task when independent lifecycle or retrieval justifies it. That
promotion allocates a new Work ID; it does not create one external file per
ordinary Plan Task.

## 10. Publication

A consuming repository may choose its own distribution policy, but this
Documentation System's Skill Distribution omits any path with a dot-prefixed
component. Therefore `.project/` and every descendant are absent from
`latest` without an additional exclusion list.

Do not move current Work Management guidance itself under `.project/`.
Guidance belongs in the published Work Management root; mutable instances belong
in the sideband.

# 📖 Project Storage

## 1. Storage root

A repository that owns its Work Management state stores it beneath the reserved
`.project/` sideband.

The sideband gives work one deterministic resumability root, separates mutable
work state from current product authority, remains address-opaque, and is
omitted from this repository's dot-prefixed distribution projection.

Retained Records such as Feedback, Issue, Fault Record, and Research are not
placed under `.project/` merely because work may derive from them.

## 2. Canonical project skeleton

```text
.project/
├── README.md
├── metrics.json
├── Planning/
│   ├── Plans/
│   ├── Investigations/
│   └── Decisions/
├── Execution/
│   ├── Tasks/
│   └── Handoffs/
└── Archive/
    ├── Planning/
    │   ├── Plans/
    │   ├── Investigations/
    │   └── Decisions/
    └── Execution/
        ├── Tasks/
        └── Handoffs/
```

Git may retain empty leaves with `.gitkeep` anchors.

Legacy `.project/Intake/` trees may remain in repositories that already carry
historical Idea, Feedback, Issue, or Fault Work Objects. Current setup does not
create that branch, and current Records should not be added there.

## 3. Responsibility layer

- **Planning** stores Plans, Investigations, and work-facing Decisions.
- **Execution** stores standalone Tasks and independent Handoffs.
- **Archive** stores cold closed Work Objects after lifecycle close-out.

Lifecycle states do not create status directories.

## 4. Stable placement

Normal state changes do not move a Work Object between folders. Archive movement
occurs only when close-out selects cold retention.

Plan-local Tasks remain inside their Plan and never receive standalone storage
merely because they are executable.

## 5. Controlled sideband behavior

Document Control recognizes `.project` as a controlled sideband. Supported
metadata-bearing artifacts may receive UIDs and validation without acquiring a
Documentation System address or generated Index entry.

Folder normalization does not rename the sideband or descendants.

## 6. Work ID allocator metrics

`.project/metrics.json` is repository-automation state.

Version 2 records active counters:

```json
{
  "version": 2,
  "ids": {
    "investigation": 1,
    "decision": 1,
    "plan": 3,
    "task": 1,
    "handoff": 1
  }
}
```

The counter is not proof that an ID is unused. Automation validates against
active and archived Work Objects before allocation.

Version 1 metrics are a migration input. Reconciliation preserves the active
counters for Investigation, Decision, Plan, Task, and Handoff while dropping
Idea, Feedback, Issue, and Fault from the active allocator schema.

Historical IDs are never recycled.

## 7. Naming and registration

Standalone Work Objects begin with their Work ID followed by a concise title.

Current prefixes are `R` Investigation, `D` work-facing Decision, `P` Plan,
`T` Task, and `H` Handoff.

Use Work automation to register standalone Tasks and Plans. Plan-local Task IDs
such as `T1` remain scoped to their Plan and do not use the allocator.

## 8. Legacy record-like Work Objects

Automation continues to recognize legacy Idea, Feedback, Issue, and Fault Work
IDs so existing repositories can validate and migrate retained history without
renumbering it.

Legacy recognition does not make those kinds current Work Object categories and
does not create active counters or Intake folders for new instances.

## 9. Publication

This repository's Skill Distribution omits paths with dot-prefixed components,
so `.project/` remains absent from `latest`.

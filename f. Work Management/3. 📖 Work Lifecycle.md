# 📖 Work Lifecycle

## 1. Work Object

A Work Object is repository-local working information whose primary job is to
carry executable, coordinating, investigative, decision, or continuation state
independently of conversational context.

A retained Record is not a Work Object merely because work may derive from it.
Feedback, Issue, Fault Record, and Research records preserve information under
their Document Forms. When they require action, relate them to the Work Object
that carries the executable state.

Every standalone Work Object has controlled identity, a stable Work ID, a kind,
current lifecycle state where applicable, and an updated time.

Plan-local Task IDs are not standalone Work IDs.

## 2. Work Object kinds

The common Work Management kinds are:

| Kind | Meaning |
| --- | --- |
| `investigation` | Bounded work to reduce uncertainty before another commitment can safely occur. |
| `decision` | Work-facing choice constraining a Plan or standalone Task; durable architectural provenance remains an ADR when its Form applies. |
| `plan` | Coordinated execution model for one outcome with multiple acceptance boundaries. |
| `task` | Independently executable repository work with standalone lifecycle and retrieval identity. |
| `handoff` | Independent continuation package when separate identity and retrieval are justified. |

A deliverable is normally an output relation, not a Work Object kind. Draft is
artifact maturity, not lifecycle state. Review and Validation are activities or
Gates unless their execution needs independent standalone work.

## 3. Standalone Task and Plan-local Task

A standalone Task has repository-global identity such as `T043`. A Plan-local
Task is owned by one Plan, uses a local identifier such as `T1`, and has no
repository-global Work ID.

Create a standalone Task when its execution, retrieval, blocking, handoff,
review, close-out, or relations must survive independently of one Plan.

## 4. Step

A Step is an execution action inside one Task acceptance boundary. It has no
independent lifecycle, disposition, Work ID, or file.

If an action needs independent blocking, handoff, cancellation, review, or
acceptance, represent it as a Task rather than extending Step state.

Document Forms own Step source representation.

## 5. Lifecycle state

The common standalone state vocabulary is:

| State | Meaning |
| --- | --- |
| `captured` | Recorded, but actionability has not been established. |
| `ready` | Acceptance is understood and starting prerequisites are satisfied. |
| `active` | Work currently holds execution attention. |
| `blocked` | A named unsatisfied condition prevents progress. |
| `review` | Primary execution is complete and a required review or validation Gate remains. |
| `closed` | The object no longer competes for active attention and has a disposition. |

Plan-local Tasks use Planning's narrower state vocabulary.

State is canonical information. Filesystem placement and Form presentation may
project state but must not contradict it.

## 6. Disposition

A closed standalone Work Object records one disposition:

| Disposition | Meaning |
| --- | --- |
| `completed` | Acceptance conditions were satisfied. |
| `cancelled` | Work intentionally ended without satisfying the original acceptance boundary. |
| `rejected` | Proposed work was considered and declined. |
| `duplicate` | Another Work Object owns the surviving work. |
| `superseded` | A newer object or approach replaces this one. |
| `converted` | This object intentionally became another work kind or object. |
| `deferred` | Active attention ended until a named future condition permits reconsideration. |

`closed` without a disposition is incomplete close-out.

## 7. Relation

Relations are named graph edges between Work Objects and relevant Records or
controlled artifacts. Prefer the smallest vocabulary that preserves an
execution decision.

Common relations include `concerns`, `derives-from`, `requires`,
`enables`, `blocks`, `coordinates`, `produces`, `validates`,
`resolves`, `remediates`, `supersedes`, and `duplicates`.

Containment and matching filenames do not replace an explicit relation when the
edge matters to execution or provenance.

## 8. Gate

A Gate is a checkable condition controlling whether downstream work may start or
close. It states the observable condition, evidence location, and minimum
sufficient threshold.

Priority cannot override an unsatisfied Gate.

## 9. Execution frontier

The execution frontier is the derived set of incomplete executable work whose
prerequisites and Gates are satisfied and which has no active blocking
condition.

Queue, ready list, and blocked list are projections over canonical work state.

## 10. Artifact maturity

Artifact maturity is independent from work lifecycle. Do not encode draft,
candidate, or final artifact maturity as Task state.

## 11. Retention

`retention: active` keeps a closed Work Object in its normal responsibility
store. `retention: cold` selects archival storage under `.project/Archive/`.

Moving to Archive changes retrieval treatment, not identity or disposition.

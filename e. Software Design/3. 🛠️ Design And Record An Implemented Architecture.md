# 🛠️ Design And Record An Implemented Architecture

## 1. Confirm that architecture is warranted

Identify the interacting design decisions that future work must preserve.
Create durable architecture only when those decisions extend beyond one local
contract or would otherwise require a maintainer to reverse engineer intent from
implementation.

Name the implementation scope whose future changes depend on those decisions.

## 2. Choose the owning root

Find the nearest stable implementation root that owns the architectural scope.
Use or create its `📐 Architecture/` store.

Follow the host repository's organization scheme when representing that
directory. In an ordinal-controlled corpus, add the local ordinal required by
that scheme rather than making the Architecture store address-transparent.

If a narrower implementation root already has architecture, decide explicitly
whether the new architecture specializes, replaces, or remains independent of
it.

## 3. Establish drivers before structure

Identify the consumers, required capabilities, constraints, quality goals,
ownership boundaries, and externally imposed conditions that actually select the
architecture.

Consult
<a href="2.%20%F0%9F%93%96%20Software%20Design%20Principles.md" uid="M8MDHY">documentation-system:§e.2</a>
and the applicable recurring Software Design concerns before choosing module,
class, framework, transport, persistence, or deployment representations.

Use architecture viewpoints, perspectives, and other completeness lenses to
probe for material concerns that the initial problem statement may have missed.
Do not copy those lenses into the final document as empty headings.

## 4. Select reusable architecture deliberately

Check whether an established Software Design architecture has selecting
conditions that match the implementation.

Select it only when the implementation accepts its fixed obligations. Record the
selection in the Architecture Document and identify the local realization and
verification evidence.

When no reusable architecture fits, resolve the concern directly from its
Reference rather than claiming approximate conformance.

## 5. Resolve the implemented design

Fix the architecture at the level future maintainers need:

- responsibility and ownership;
- canonical state and invariants;
- component or module boundaries;
- interaction and dependency rules;
- external boundaries and translation;
- relevant failure, persistence, concurrency, security, operational, or quality
  behavior;
- deliberate extension points and allowed variation.

Prefer statements that constrain future implementation choices. Remove
descriptions that merely restate the current file tree without explaining a
durable design boundary.

## 6. Map architecture to implementation

Identify the code structures that realize each load-bearing architectural
concept.

Use paths, entry points, modules, schemas, interfaces, registries, processes, or
other stable source-addressable boundaries where doing so lets an amnesiac
maintainer move directly from architectural claim to implementation evidence.

Do not make moving line numbers or incidental private helper names durable
architecture identifiers.

## 7. Define verification

For every architectural claim whose violation can be detected mechanically,
identify the check that proves it.

For behavioral obligations, identify the independent contract and faithful test
boundary. For structural obligations, prefer import, schema, declaration,
dependency, or source-shape checks when those structures are intentionally part
of the architecture.

Expose architectural claims that currently lack executable verification rather
than silently treating documentation as proof.

## 8. Author the Architecture Document

Use the
<a href="../a.%20Document%20Design/a.%20Assemblies/b.%20Forms/b.%20Architecture%20Document/README.md" uid="T6P28F">documentation-system:§a.a.b.b</a>
Form.

Write the required Scope, Drivers, Architecture, Realization, Verification, and
Evolution surfaces. Keep their content proportional to the implemented design;
do not manufacture detail for irrelevant concerns.

Bind the document to the Form and retain current architecture as Reference
authority.

## 9. Declare and route the architecture

Ensure the Architecture store README routes to each current Architecture
Document.

Where controlled implementation metadata is supported, add a direct
`architecture` link at the public or indexed entry point. In this repository,
use a UID-controlled link so Organizing can refresh the physical path and
locator when the Architecture Document moves.

Internal implementation inherits the nearest governing architecture unless a
narrower architecture states otherwise.

## 10. Preserve rationale separately when useful

Create an ADR when a consequential choice has historical reasoning worth
retaining. Keep the Architecture Document focused on the design that governs
now.

Do not require an ADR for every architecture edit and do not leave a current
architectural rule available only through ADR history.

## 11. Validate the result

Run the repository's organization and verification workflows after creating,
moving, or changing architecture authority.

Finish when:

- the Architecture Document is controlled and normally discoverable;
- its Form provenance resolves;
- its Scope identifies the governed implementation;
- direct architecture links resolve where required;
- realization evidence is locatable;
- verification obligations are explicit; and
- code and current architecture make the same claims.

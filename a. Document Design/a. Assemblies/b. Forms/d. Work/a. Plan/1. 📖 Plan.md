# 📖 Plan

> [!WARNING]
> A Plan that is relied on for execution must exist in durable storage available
> to the executing agent after conversation compaction, interruption, or
> handoff. Chat-only or otherwise transient Plan state is not a valid continuity
> source.

## 1. Scope

This Form governs Markdown source representation for a Work Management Plan.

It does not define Planning semantics. Work Management Planning owns Plan-local
Task identity, state meaning, Steps, relations, Gates, promotion, execution
frontier, and lifecycle boundaries.

## 2. Terms

| Term | Meaning |
|---|---|
| **plan-authoring work** | Work required to discover, reason about, validate, and record a trustworthy Plan. |
| **planned work** | Work represented by the Plan as Tasks and Steps whose completion contributes to the Plan outcome. |
| **preparation** | Plan-authoring work completed before executable decomposition is treated as authoritative. |
| **discovered work** | Planned work revealed by guidance, repository inspection, capability constraints, or execution tracing rather than stated explicitly in the initial request. |

Do not represent plan-authoring preparation as Plan Tasks merely because the
author had to perform it. Record an activity as planned work when it
independently contributes to the Plan outcome.

## 3. Durable envelope

For repository-local Work Management, store the Plan beneath
`.project/Planning/Plans/` using the repository's supported identity and
registration mechanism.

When that repository store is unavailable to the authoring environment, another
durable artifact store available after conversation compaction may temporarily
hold the Plan. Make that limitation explicit. Do not manually invent a Work ID
to imitate unavailable repository automation.

A standalone Plan carries its normal controlled metadata and `work:` mapping.
When Document Form provenance is supported, record this Form package and version.

Use the Plan Work ID in the H1 when one has been allocated:

```markdown
# P004 — Replace parser architecture
```

## 4. Whole-document sections

Use these primary sections when applicable:

```markdown
## Outcome
## Acceptance conditions
## Constraints
## Decisions
## Execution-environment check
## Tasks
## Current state
## Next action
```

Outcome, Acceptance conditions, Tasks, Current state, and Next action are
normally required for an active Plan.

## 5. Execution-environment check

Every Plan retains an early instruction requiring the current executor to assess
its own harness before entering the execution frontier. The authoring agent's
tool inventory is not reusable execution truth.

Prompt the executor to consider only materially relevant capabilities and
limitations, including bounded reads and EOF behavior, search limits,
conversation/output limits, durable storage, repository checkout availability,
code execution and timeouts, dependency and network availability, connector
permissions, mutation authority, external calls, and specialized tools.

Retain specific capability facts only when they affect execution, blocking,
validation, handoff, or acceptance.

## 6. Task heading

Each Plan-local Task begins with an H3 outside its state callout:

```markdown
### T3 — Add explicit Work Management project setup
```

Use compact Plan-local IDs in Plan order. Do not use zero-padded
repository-global `T###` identifiers for Plan-local Tasks.

## 7. Ready Task

Represent a ready Task as:

```markdown
### T3 — Add explicit Work Management project setup

> [!NOTE] State: Ready
>
> **Acceptance**
> - A repository can adopt Work Management through one setup procedure.
>
> **Steps**
> - [ ] Add Set Up Work Management.
> - [ ] Define the complete project skeleton.

---
```

## 8. Active, blocked, and review Tasks

Use a state-appropriate callout immediately below the Task heading.

- Active: `> [!IMPORTANT] State: Active`
- Blocked: `> [!WARNING] State: Blocked`
- Review: `> [!CAUTION] State: Review`

The explicit state text is canonical. The callout increases salience; it does
not replace state semantics.

## 9. Acceptance and Steps inside a callout

Keep the Task acceptance conditions and current Steps inside the Task state
callout while the Task is non-terminal.

Every Step MUST be a Markdown task-list checkbox or be immediately accompanied
by the checkbox that carries its completion state. Plain numbered or bulleted
action lists do not satisfy the Step representation contract.

## 10. Completed Task

A completed Task is not quoted and does not use an alert callout. Strike through
the completed Task representation so settled work remains visible without
competing with active attention. Keep completed Step checkboxes checked and
retain useful completion evidence.

## 11. Task boundary

Terminate every Plan Task block with a Markdown horizontal rule:

```markdown
---
```

## 12. Dependencies and Gates

Represent dependencies and Gates close enough to the affected Task that an
executor can recover the prerequisite without searching the whole file.

Use concise properties or a dedicated Gates section when several Tasks share the
same condition. Do not duplicate one Gate in several independently maintained
places.

## 13. Current state and next action

After the Task sequence, summarize the execution frontier and continuation
context under Current state.

Next action names the next concrete operation an unfamiliar agent can perform.
These sections are resumability aids, not replacements for canonical Task state.

## 14. Completion condition

A Plan file conforms when:

- its persistence is durable enough for execution continuity;
- its Plan identity and outcome are recoverable;
- its executor capability check is present;
- every Plan-local Task has one local ID and explicit state;
- every non-terminal Task uses the state callout convention;
- every completed Task is unquoted and struck through;
- every Step is checkbox-backed;
- every Task block ends with `---`;
- Task acceptance boundaries are explicit; and
- current state and next action make continuation possible without prior
  conversation.

# 🛠️ Author A Plan

## 1. Resolve Plan semantics first

Use Work Management Plan Work and Plan Model to establish the outcome, Plan-local
Tasks, acceptance boundaries, dependencies, Gates, and current execution state.

Do not use this Form to invent work decomposition.

## 2. Create the Plan envelope

Create one Plan Markdown file beneath the repository's
`.project/Planning/Plans/` store.

Add the standalone Plan Work Object metadata and H1.

Bind Form provenance when the host corpus supports controlled Form mappings.

## 3. Write Plan outcome and constraints

Write the Plan outcome and acceptance conditions before the Task sequence.

Record only constraints and decisions that affect execution or handoff.

## 4. Create each Task heading

Use an H3 with the Plan-local ID and concise acceptance-boundary title:

```markdown
### T1 — Reconcile Work Management semantics
```

Keep the heading outside the state callout.

## 5. Render non-terminal Task state

Immediately beneath the heading, use the callout matching current state:

- Ready: `> [!NOTE] State: Ready`
- Active: `> [!IMPORTANT] State: Active`
- Blocked: `> [!WARNING] State: Blocked`
- Review: `> [!CAUTION] State: Review`

Put Acceptance and Steps inside the callout.

## 6. Write checkbox-backed Steps

Represent every Step with Markdown task-list syntax:

```markdown
> - [ ] Incomplete action.
> - [x] Completed action.
```

When a Step requires several explanatory lines, keep the checkbox as the state
carrier and indent the explanation beneath it.

Do not create a separate state field for a Step.

## 7. Render completed Tasks

Remove the callout when a Task reaches Completed.

Strike through its heading, state, acceptance information, and explanatory text.
Keep completed Step checkboxes checked and strike through their text.

Retain enough completion evidence for handoff or auditability.

## 8. Separate every Task

Place `---` after every Task block, including the final Task before Current
state.

Do not use the separator as Task state; it is only a visual boundary.

## 9. Maintain dependencies and Gates

Keep Task prerequisites and Gates current with the semantic Plan.

When a local Task is promoted to a standalone Task, replace duplicate lifecycle
content with a reference to the registered standalone Work ID.

## 10. Maintain resumability

Update Current state and Next action whenever the execution frontier materially
changes.

An unfamiliar agent should be able to identify active attention, blocked work,
settled work, and the next safe action from the Plan alone.

## 11. Validate representation

Before handoff or close-out, verify:

- headings are outside callouts;
- state callouts match semantic state;
- every Step is checkbox-backed;
- completed Tasks are unquoted and struck through;
- every Task ends with `---`; and
- no Plan-local Task has been assigned a repository-global Work ID merely for
  formatting convenience.

# 📖 Plan

## 1. Scope

This Form governs Markdown source representation for a Work Management Plan.

It does not define Plan semantics. Work Management's Plan Model owns Plan-local
Task identity, state meaning, Steps, relations, Gates, promotion, and lifecycle
boundaries.

## 2. Frontmatter and title

A standalone Plan Work Object carries its normal controlled metadata and
`work:` mapping.

When the host corpus supports Document Form provenance, record this Form package
and the Form version used.

Use the Plan Work ID in the H1:

```markdown
# P004 — Replace parser architecture
```

## 3. Whole-document sections

Use these primary sections when applicable:

```markdown
## Outcome
## Acceptance conditions
## Constraints
## Decisions
## Tasks
## Current state
## Next action
```

Omit an optional section only when it has no information job. Outcome, Acceptance
conditions, Tasks, Current state, and Next action are normally required for an
active Plan.

## 4. Task heading

Each Plan-local Task begins with an H3 outside its state callout:

```markdown
### T3 — Add explicit Work Management project setup
```

Use compact Plan-local IDs in Plan order. Do not use zero-padded
repository-global `T###` identifiers for Plan-local Tasks.

## 5. Ready Task

Represent a ready Task as:

```markdown
### T3 — Add explicit Work Management project setup

> [!NOTE] State: Ready
>
> **Acceptance**
> - A repository can adopt Work Management through one setup procedure.
>
> **Steps**
> - [ ] Add Set Up Work Management.
> - [ ] Define the complete project skeleton.

---
```

## 6. Active, blocked, and review Tasks

Use a state-appropriate callout immediately below the Task heading.

Active:

```markdown
> [!IMPORTANT] State: Active
```

Blocked:

```markdown
> [!WARNING] State: Blocked
```

Review:

```markdown
> [!CAUTION] State: Review
```

The explicit state text is canonical. The callout increases salience; it does
not replace state semantics.

## 7. Acceptance and Steps inside a callout

Keep the Task acceptance conditions and current Steps inside the Task state
callout while the Task is non-terminal.

Every Step MUST be a Markdown task-list checkbox or be immediately accompanied
by the checkbox that carries its completion state:

```markdown
> **Steps**
> - [x] Add the adapter interface.
> - [ ] Wire the parser implementation.
```

Plain numbered or bulleted action lists do not satisfy the Step representation
contract.

## 8. Completed Task

A completed Task is not quoted and does not use an alert callout.

Strike through the completed Task representation so settled work remains visible
without competing with active attention:

```markdown
### ~~T2 — Implement adapter~~

~~State: Completed~~

~~**Acceptance**~~

- ~~Adapter satisfies the parser contract.~~

~~**Steps**~~

- [x] ~~Add adapter interface.~~
- [x] ~~Wire parser implementation.~~
- [x] ~~Run regression tests.~~

---
```

Do not remove useful completion evidence merely to shorten the Plan.

## 9. Task boundary

Terminate every Plan Task block with a Markdown horizontal rule:

```markdown
---
```

The rule belongs after completed Tasks as well as non-terminal callouts.

## 10. Dependencies and Gates

Represent dependencies and Gates close enough to the affected Task that an
executor can recover the prerequisite without searching the whole file.

Use concise properties or a dedicated Gates section when several Tasks share the
same condition. Do not duplicate one Gate in several independently maintained
places.

## 11. Current state and next action

After the Task sequence, summarize the execution frontier and continuation
context under Current state.

Next action names the next concrete operation an unfamiliar agent can perform.

These sections are resumability aids, not replacements for the canonical state
inside each Task.

## 12. Completion condition

A Plan file conforms when:

- its Plan identity and outcome are recoverable;
- every Plan-local Task has one local ID and explicit state;
- every non-terminal Task uses the state callout convention;
- every completed Task is unquoted and struck through;
- every Step is checkbox-backed;
- every Task block ends with `---`;
- Task acceptance boundaries are explicit; and
- current state and next action make continuation possible without prior
  conversation.

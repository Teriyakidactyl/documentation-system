# 📖 Glossary

## Purpose

A Glossary is a heading-bounded reader-orientation surface. It defines the
project-specific terms and concepts a reader needs at the current document
boundary. It is not a repository-wide dictionary and does not expose deeper
vocabulary merely because that vocabulary exists elsewhere in the project.

Progressive disclosure determines the glossary's knowledge horizon. A reader
should acquire a term when its project-specific meaning becomes necessary to
use the current document correctly or to navigate successfully to the next
owning guidance, not simply because the term may matter later.

## Entry selection

Evaluate every candidate from the arriving reader's perspective. Include it only
when all four conditions hold:

| Test | Include when |
|---|---|
| **Current scope** | The term or concept affects correct use or understanding of this document. |
| **Knowledge horizon** | The reader must understand it before this document or normal progressive disclosure can carry them to narrower guidance. |
| **Project-specific meaning** | The project assigns a meaning, distinction, or behavioral consequence that ordinary language or expected domain knowledge does not reliably supply. |
| **Deferral** | Deferring the definition would impair correct use here; otherwise let the narrower owning document define it when needed. |

Do not include a term merely because it appears in the document, is important
somewhere in the project, or names an implementation detail familiar to the
author. Before glossarying a representation or maintainer term, ask whether the
reader-facing prose can state the required behavior without exposing that
vocabulary. Keep the term only when the reader must recognize or act on the
project-specific concept itself.

## Definition depth

Define an included entry only to the depth required for correct use at the
current knowledge horizon. A local definition may be narrower than the complete
canonical model owned elsewhere, but it must remain compatible with that model.

Do not duplicate the owning Reference merely to make the current document
self-contained. Link to deeper guidance when the reader needs the complete
model. Use one canonical name per concept and preserve established
project-defined terms and exact referents.

## Representation

Choose representation only after the entry set is stable.

| Entry set | Representation |
|---|---|
| One local term | Define it inline; a Glossary Element instance is unnecessary. |
| Small peer set | Use a two-column `Term | Meaning` table. |
| Relationships are load-bearing | Add a relationship tree before the two-column definition table. |
| Repeated attributes are the primary lookup task | Use the Semantic Registry Element instead of forcing those attributes into a glossary table. |

A Glossary instance may therefore be a simple table or a relationship tree plus
table. The representation serves the selected concepts; it does not determine
which concepts belong.

When relationships are required for correct interpretation, preserve them
before the same definition surface:

````markdown
```text

```

| Term | Meaning |
|---|---|
| **request** | One unit of work entering the system. |
| **identity** | The durable identifier carried by the request. |
| **routing** | The project-defined rule that selects the request's destination. |
````

## Constraints

Keep definitions reader-facing and prose-oriented. Keep a relationship tree and
its table in the same order when practical. Place the glossary at the document
boundary before later content whose correct use depends on its project-specific
meanings. A short framing statement that establishes the reader interaction
model may precede the glossary when that framing explains why the glossary is
localized.
